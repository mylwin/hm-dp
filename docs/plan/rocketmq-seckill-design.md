## 1. 范围与选择

以当前 hm-dp 为迁移基线，借鉴同级 hmdp-plus 的 Redis 资格预扣、MQ 异步建单、流水与补偿思路。
保留普通券发布、秒杀券发布、店铺券列表、登录后抢券、一人一单、数据库防超卖和返回订单编号。
补齐可靠受理、结果查询、重试、补偿、对账、迁移与运行维护。

hmdp-plus 的用户等级、订阅自动发券、取消后再购、分片路由并非当前项目已有功能，不作为本次迁移验收范围。
当前实体虽有支付、退款状态字段，但仓库没有对应完整业务接口，本设计不声称已经实现支付、退款或支付超时关单。

推荐采用 **RocketMQ 普通消息 + MySQL 请求账本 + Outbox + Redis 按订单预占状态**。
此选择保留原项目的业务分工，改变其“Lua 后直接异步发送，失败就回滚”的实现。
第一阶段不同时引入 RocketMQ 事务消息，也不保留 Stream 作为日常投递缓冲。

取舍：候选抢购请求会新增数据库受理记录，增加写入和连接占用；不能沿用原有纯 Redis 请求路径的吞吐假设。
入口限流、Redis 只读预检可以减少无效请求，但不能替代最终原子校验。
数据库压力若经压测不可接受，再另行评估事务消息路线；不能为了保持纯 Redis 性能而省掉可靠性边界。

## 2. 必须成立的规则

1. 相同 requestId 的重试绑定同一用户、同一券、同一 orderId；参数冲突拒绝。
2. 返回受理成功之前，ACCEPTED 状态与待发事件必须已经在同一个 MySQL 事务中提交。
3. 订单创建、数据库库存扣减、请求成功终态在同一个事务中提交。
4. 同一个用户同一张券最多有一张订单；当前业务不引入取消后再购。
5. 请求关闭与订单创建竞争同一请求行锁，只有一方能提交；关闭后迟到消息不得建单。
6. 一个预占最多释放一次；已经成功建单的预占不得回补。
7. 发送失败、发送超时、数据库暂时故障、进入死信，都不等于业务取消。
8. 队列是可重放的投递通道；MySQL 是受理结果、订单结果和恢复任务的事实来源。
9. Redis 不可用时拒绝新预占或保持处理中，不静默降级为无保护的直接落库。

## 3. 最小数据模型

### MySQL

- `tb_seckill_campaign_control`：voucher_id 主键、代次、维护状态。专门协调共享/排他维护锁，避免在库存行上先共享锁再升级写锁。
- `tb_seckill_request`：order_id 主键，user_id、voucher_id、request_id、payload_hash、状态、失败原因、预占代次、创建/更新时间、版本。
  `UNIQUE(user_id, request_id)` 负责请求重试去重；`(status, updated_at, order_id)` 支持恢复扫描。
- `tb_mq_outbox`：event_id 主键，order_id、事件类型、schema_version、消息体、投递状态、next_retry_at、重试次数、租约持有者/到期时间。
  `UNIQUE(order_id, event_type)` 防止同一逻辑事件重复登记；数据库中保留发送确认记录。
- `tb_voucher_order`：保留现有 order_id 主键，迁移前核对并新增 `UNIQUE(user_id, voucher_id)`。
- 补偿任务复用 Outbox 的独立事件类型及任务执行器；失败原因、尝试次数、下次重试时间持久化。

不要把请求处理状态直接塞进现有订单支付状态字段。
状态为 `PREPARING → ACCEPTED → SUCCEEDED`；PREPARING 可进入 REJECTED/CLOSED，ACCEPTED 在明确业务失败或显式关闭时进入 CLOSED。
补偿另有 PENDING/DONE/FAILED 状态；“请求已关闭”与“Redis 已恢复”分别记录。
请求表允许失败后使用新 requestId 再尝试，成功订单的业务唯一索引仍兜底一人一单。

### Redis

同一券相关键使用共同 hash tag，Lua 的全部键通过 KEYS 传入，例如 `hmdp:seckill:{voucherId}:...`。

- 可用库存、活动元数据、当前代次和 READY 标志。
- 用户资格映射：`userId → orderId`，替代只记录 userId 的 Set，保证补偿不会误删新的请求资格。
- 按 orderId 记录的预占：RESERVED/CONFIRMED/RELEASED/REJECTED，含用户、券、代次和数量。
- 流水用于审计与诊断；数量前后值不是补偿时可以直接覆盖库存的目标值。

处理中记录不按短 TTL 任意删除；终态保留期覆盖消息重放、任务重试及人工恢复窗口。
过期后的历史消息仍必须查询 MySQL 终态，不能因 Redis 标记缺失而重新建单或回补。

## 4. 请求受理协议

1. 鉴权、参数校验、限流、检查活动元数据是否就绪；Redis 预检仅用于尽早拒绝。
2. 生成或读取 requestId 对应的 orderId，提交 PREPARING 请求记录；已有记录按状态返回。
3. 开启短事务，先取得该券维护协议的共享锁，再锁定请求行，确认仍是 PREPARING。
4. 在有界超时内执行预占 Lua：校验 READY、代次、活动时间、库存、用户资格和 orderId 终态。
   首次成功时扣库存并记 RESERVED；同一 orderId 重入返回原结果；RELEASED/REJECTED 不允许重新预占。
5. 成功后，在当前 MySQL 事务中更新 ACCEPTED，并插入 CREATE_ORDER Outbox，再提交。
6. 提交成功才返回现有 `Result.ok(orderId)`；提交结果未知时按 requestId 查账本，不生成新订单。

步骤 3 会在持有数据库请求行锁期间调用 Redis，这是为序列化受理与恢复付出的代价。
必须限制 Redis 调用与数据库锁等待，避免长事务；严禁在此事务中等待 MQ 网络操作。
本协议不是 Redis 与 MySQL 的原子事务，中间差异由 PREPARING 账本和恢复任务消除。

Lua 超时不能认定没有预扣。事务回滚后 PREPARING 记录仍在，恢复程序能识别这个未完成请求。
恢复程序与在线请求使用同一维护协议及请求行锁：发现 RESERVED 可完成 ACCEPTED + Outbox；明确拒绝则标记 REJECTED。
若需要关闭不确定请求，先在 MySQL 提交 CLOSED 和补偿任务，再执行释放 Lua。
释放 Lua 即使未发现预占，也写 RELEASED 墓碑，阻止已超时但随后才执行的预占命令。
已经 RESERVED 则按 orderId 释放一次；不能采用“查不到记录就当补偿完成”的方式。

## 5. Outbox 与 RocketMQ

事件建议包含 eventId、orderId、userId、voucherId、schemaVersion、acceptedAt、traceId。
消息业务标识使用 orderId/eventId；Broker messageId 不承担业务幂等职责。

- 订单 Topic 与消费者组独立，例如 `hmdp-seckill-order-create` / `hmdp-seckill-order-create-cg`。
- 采用集群消费；普通订单创建消息不强制按 voucherId 全部串行，数据库条件扣减和唯一约束兜底。
- 发布任务短事务领取有租约的 Outbox 记录，事务外发送，收到成功确认再更新 SENT。
- 发送超时或失败只更新退避时间；不得据此释放库存。
- Broker 已收、进程在写 SENT 前退出时会重复发送，用相同 eventId/orderId 恢复。
- 租约更新和 SENT 写入校验租约令牌，防止旧发布者覆盖新发布者的任务状态。
- SENT 只表示一次投递确认，不是订单终态；ACCEPTED 长期无结果时仍需检查并恢复投递。

客户端使用已验证的原生 RocketMQ 5.3.2，当前 Broker 同为 5.3.2，不依赖 gRPC Proxy。
Java 17/Spring Boot 3.5.9 下已验证客户端、真实探针收发及第二阶段隔离投递，正式订单消费仍属于后续阶段。

## 6. 订单消费与幂等

1. 校验消息版本和必填字段，锁定请求行，核对消息与账本中的用户、券、订单一致。
2. SUCCEEDED：返回成功；CLOSED/REJECTED：结束处理；PREPARING：重试或交恢复任务，不能擅自创建。
3. ACCEPTED：在同一本地事务中执行库存条件扣减、订单插入、请求改 SUCCEEDED、登记 Redis 确认任务。
4. 等数据库事务提交成功后才向 MQ 返回成功；提交结果未知允许重投并查询账本。
5. Redis 确认任务将预占转 CONFIRMED，不再减少 Redis 可用库存；任务失败可持久化重试。

相同订单重复投递必须是成功处理，不能抛“用户已购买”并进入回补流程。
不同 orderId 命中相同用户/券时，以已有订单为准，关闭冲突请求并释放它自己的预占。
唯一键冲突、保存失败必须让库存扣减事务回滚，然后在新事务中判定处理结果。
Redis 分布式锁可用于减轻竞争，但不能替代数据库业务约束和事务。

临时故障重试；确定无法创建时，原创建事务回滚，再以请求行锁进入 CLOSED 并登记释放任务。
MQ 达到重试上限进入死信后告警，恢复程序仍按账本处理；死信不触发无条件释放。
非法/不支持的消息需可靠隔离并告警，不能无限阻塞整个消费链路。

## 7. 补偿与库存恢复

关闭程序和消费者争用同一 MySQL 请求行锁：

- 消费者先提交 SUCCEEDED：关闭程序不得回补。
- 关闭程序先提交 CLOSED：迟到消费者只能结束处理。

释放 Lua 按 orderId 校验预占、数量、代次和用户资格拥有者。
RESERVED 首次转 RELEASED 才回补；已 RELEASED 重试不变；CONFIRMED 拒绝回补并告警。
用户映射只有仍等于这个 orderId 才删除；不能按 userId 无条件清除。
脚本调用结果未知仍用原任务标识重试，不能新建一笔无关联的回补操作。

禁止复制 hmdp-plus 的“每次补偿删除整张券库存，再直接从 DB 加载”的策略：
DB 库存尚未反映所有在途请求，直接覆盖会重新放出已预占额度。

Redis 重启、键丢失或人工重建必须走受控维护：

1. 停止该券的新受理，维护写锁与受理/消费/关闭的共享协议协调，等待在途事务退出。
2. 对 PREPARING 记录明确恢复或关闭，取得一致的数据库库存和仍为 ACCEPTED 的请求集合。
3. 新代次可用库存 = 数据库剩余库存 - 尚未落库的有效预占数量；异常负数应停止开放并告警。
4. 重建用户资格映射、有效预占记录及必要终态映射，不只恢复一个库存数字。
5. 原子发布新代次及 READY 后恢复请求；所有修改脚本检查代次，拒绝迟到的旧代次写入。
6. 尚未执行的确认/补偿任务通过稳定 orderId 查新代次映射后重试，不能操作已废弃计数器。

维护协议必须涵盖全部库存与请求终态写入口；只有普通分布式锁而无代次隔离，不能防止暂停后恢复的旧进程写入。
当前单库实现可以在事务内使用独立活动控制行的共享锁/排他锁协调维护，统一按“活动控制 → 请求 → 库存/订单”的顺序加锁。
控制行与真实库存行分离，避免多个消费者同时先持库存共享锁再尝试升级写锁造成锁升级死锁。
重建须先解决同用户同券的冲突候选，再生成唯一资格映射；重建失败保持未就绪，不发布半成品。

## 8. 对账与前端闭环

实现随应用运行的周期性任务，配合多实例租约/数据库领取机制，并保留有权限控制的手动入口。
按索引分页、限速扫描，避免全量读取全部券和全部流水。

| 账本状态/现象 | 恢复操作 |
|---|---|
| PREPARING 长期未推进 | 请求行锁内核对预占，继续受理或关闭并登记补偿 |
| Outbox 到期未发送/租约失效 | 重新领取、按相同业务标识投递 |
| ACCEPTED 长期无终态 | 核对订单、恢复消息投递；超时先告警，不能直接释放 |
| SUCCEEDED 但 Redis 未确认 | 重试确认任务，不回补库存 |
| CLOSED 且补偿未完成 | 重试原释放任务，直至完成或人工处理 |
| Redis 全部状态丢失 | 暂停新预占，执行受控重建 |
| 死信 | 按账本重投或显式关闭，保留审计记录 |

增加鉴权接口 `GET /voucher-order/requests/{orderId}`，只允许所属用户查询。
返回 PROCESSING/SUCCEEDED/FAILED、业务原因和补偿处理中提示；不能把查不到订单直接解释为失败。
提供按 requestId 恢复查询的方式，处理 HTTP 响应丢失；拒绝越权和 requestId 参数复用。
前端维持当前抢购受理展示，增加有限轮询、退避、成功/失败结果及关闭页面后的恢复入口。
前端停止轮询不等于取消后台请求；重试同一操作沿用 requestId。
原 POST 返回 orderId 的成功结构保持兼容；提交结果未知要返回可恢复的处理提示。

秒杀券发布先提交 DB，再执行可重试的 Redis 预热；元数据/库存未就绪前不能开放抢购。
发布任务也持久化，不能只依赖进程内 afterCommit 回调；该回调可用于加速触发，但不能替代恢复扫描。

## 9. 与 hmdp-plus 的功能映射

| 能力 | hmdp-plus 实现 | 本方案 |
|---|---|---|
| 时间、库存、资格判断 | Lua + Redis 流水 | 保留并增加 orderId 预占与代次 |
| 异步建单 | Kafka | RocketMQ |
| 发送失败 | 回调补偿 | Outbox 重投，未知不回补 |
| 消费失败 | 补偿后抛异常 | 临时故障重试，确定关闭后才补偿 |
| 消息年龄超过 10 秒 | 补偿并放弃创建 | 告警/限流，继续恢复；不以消息年龄自动丢单 |
| 防重复 | 消息 UUID 切面 + 订单查询 | 请求幂等 + 订单主键/业务唯一约束 + 终态 |
| 补偿 | 删除库存缓存 | 按订单幂等释放 |
| 对账 | 流水比对、手动入口 | 实际调度、分页恢复、手动维护 |
| 结果查询 | 缓存/路由表查询订单号 | 查询受理终态与失败原因，校验归属 |

这里的“完整”指当前项目迁移范围及异步故障闭环完整，不代表复制 Plus 所有业务功能。

## 10. 改动清单与迁移

- service：拆分秒杀受理、事务订单创建、关闭、恢复服务，避免 self 代理与 MQ 循环混在一个大类。
- infrastructure/mq：Producer、Outbox 发布任务、Listener、消息模型、隔离与指标。
- infrastructure/seckill：预占、确认、释放脚本和受控重建组件。
- entity/mapper/db：请求账本、Outbox、补偿任务字段、业务索引和可重复执行的迁移脚本。
- controller/frontend：requestId、结果查询、恢复入口、轮询和失败展示。
- config/compose：RocketMQ 本地依赖、Topic/消费组初始化、重试/保留期与启动健康检查。
- observability：Outbox 最老待发年龄、ACCEPTED 最老年龄、消费失败、死信、补偿待办及 DB 锁等待。
- tests/docs：真实中间件故障测试、运行与人工恢复步骤；不要将未测试场景写成已验证。

迁移步骤：

1. 扩展数据库结构，核查历史重复订单后添加唯一索引；新服务先不接流量。
2. 在维护窗口暂停秒杀新入口，消费并恢复旧 Stream 的未读与 pending 消息，记录基线。
3. 确认旧请求全部进入可解释终态，停止所有旧消费者与旧实例的下单写入。
4. 根据数据库订单/库存初始化新 Redis 代次和资格；确认 Outbox、消费者、恢复任务健康后切换流量。
5. 验证数据库数量和终态后，再移除 Stream 启动消费、常量及 Docker healthcheck 的建组依赖。

回滚要先暂停新入口，处理/关闭新链路请求并等待补偿完成，再重建旧链路状态。
不能只改配置恢复旧消费者，也不能让新旧链路对同一批请求同时执行预扣和落库。
不要求本次迁移支持无停机灰度；若未来要做，需要额外设计统一请求账本和流量归属。

## 11. 验收用例

以下为完整迁移必须执行的验收计划，尚未全部执行；第二阶段已验证的子集见阶段文档，不能替代整套订单验收：

| 用例 | 必须观察到的结果 |
|---|---|
| 正常抢券、未开始、已结束、券不存在、未就绪 | 结果明确，拒绝请求不消耗库存 |
| 库存 100、1000 个不同用户并发 | 成功订单不超过 100，DB 不负库存，剩余请求进入可查询结果 |
| 同一用户同券并发/相同 requestId HTTP 重试 | 最多一张订单；同 requestId 复用同 orderId |
| 相同 requestId 换用户或换券 | 按归属隔离或参数冲突拒绝，不能窃取结果 |
| Lua 成功、受理事务提交前进程退出 | PREPARING 被恢复或关闭，库存不永久占用 |
| Redis 超时，旧命令迟到执行 | RELEASED 墓碑/代次阻止重新预占 |
| ACCEPTED 已提交、发布前退出 | Outbox 恢复投递 |
| Broker 收到但发布者没写 SENT 就退出 | 允许重投，DB 只产生一次有效扣减与订单 |
| DB 消费事务提交、ACK 前退出 | 重投识别 SUCCEEDED，不能回补或重复扣库 |
| 消费暂时失败后恢复 | 事务回滚并重试，不提前释放资格 |
| 关闭任务与消费者并发、补偿重复/超时 | 只有一个终态，库存最多恢复一次 |
| 迟到消息、积压超过 10 秒、死信人工重放 | 已关闭不建单、已成功不补偿，处理中可恢复 |
| Redis 重启或库存/资格键丢失 | 暂停预占并受控重建，保留在途占用 |
| 补偿任务期间 Redis 断连 | 持久任务保留，恢复后完成，不以日志代替处理 |
| 券发布 DB 成功后应用退出 | 预热任务可恢复，未就绪不开放 |
| 服务多实例重启、Outbox 租约过期 | 可接管任务，无终态倒退 |
| 非法消息/不支持的版本 | 隔离、告警、可审计，不影响其他合法消息 |
| 迁移及回滚演练 | 无旧 pending 遗留，新旧链路不同时写入 |

联合断言：订单唯一、DB 库存非负、关闭请求无成功订单、受理终态和订单一致、补偿任务无永久孤儿。
库存等式必须在停止新流量、排空在途任务后的稳定边界验证，不能比较跨时刻读取的瞬时数字。

## 12. 能力边界与参考

功能完整性依赖上述代码、迁移和故障验收真正落地，文档不能替代验证。
数据库、MQ 的持久化/复制与备份策略决定灾难恢复边界；单机容器不提供生产高可用保证。
本设计处理进程退出、消息重复、网络结果未知和可恢复的中间件故障，不声称多份持久存储同时永久损坏仍零丢失。

- [RocketMQ 消费重试](https://rocketmq.apache.org/docs/featureBehavior/10consumerretrypolicy/)：重试及死信不能替代业务终态和恢复逻辑。
- [RocketMQ 发送重试](https://rocketmq.apache.org/docs/featureBehavior/05sendretrypolicy/)：SDK 重试不能替代持久化待投递记录。
- [RocketMQ 事务消息](https://rocketmq.apache.org/docs/featureBehavior/04transactionmessage/)：可作为另一条设计路线，但需要可靠本地事务结果与回查；不自动保证下游消费正确，也有事务超时边界。
